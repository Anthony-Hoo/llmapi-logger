## 1. 范围

Issue #59 描述的链路是：流式捕获 → 一次逻辑归档到热库 → 查询及导出 → 到期迁入冷归档 → 从归档恢复到 PostgreSQL。最后一环经维护者澄清后不做（3.1），本方案覆盖前四环。

关联项：

- PR #54（未合并）：把 Anthropic Messages 解析器改为 `AuditNormalizer`，`anthropic.messages` 升到 parser version 3。它的工作并入本 issue：cherry-pick 为 P1 分支的首个提交（5.8）。
- PR #55（已合并）：retention 独占 writer 事务，批量按上一批耗时自适应。本方案的“校验后移除”沿用它的批量与让路逻辑。
- 未提交的 `cmd/audit-stage`：它服务于 SQLite 到 PostgreSQL 的迁移。本方案不做恢复，用不到它的导入逻辑，两者没有依赖关系；只是本方案新增迁移版本后它的白名单要同步更新（4.5）。

## 2. 现状

### 2.1 已直接核对的事实

写入路径：

- **Body 小于 1 MiB 时，现在就只在结束时写一块。** 采集缓冲每阶段上限 1 MiB，攒满才 flush，否则等 Body 终结时强制 flush（`internal/audit/body.go:287-322`）。issue 里“逐块写 PG”只对超过 1 MiB 的 Body 成立。
- **一条成功请求至少有四次同步等待批提交。** `BeginAudit`、`FinishAudit`、`ClaimPendingParse`、`SaveParsedAudit` 都走 `submitSync`（`postgres/writer.go:76,150`，`parser_writer.go:28,60`）。writer 每批最多 64 个操作或等 5 ms，每个操作包一层 `SAVEPOINT writer_operation`（`types.go:69-70`，`open.go:23`，`writer.go:317`）。并发时不同请求的操作会合进同一个事务，所以每条 audit 的实际提交数要靠压测量，不能从代码推出。
- **raw 先写后删。** `SaveParsedAudit` 在规范化通过后删除该 audit 的全部 `body_chunks`，并把 `body_streams` 改为 `metadata`（`graph_writer.go:48-66`）。
- **处理函数返回前要等终结事务提交。** `proxy.go` 里 `defer session.Finish()`，而 `Finish` 同步等待 `FinishAuditWithResult`，没有超时（`session.go:308-435`）。所以现在处理函数一返回，采集结果已经落库。
- **父轮次选择在 writer 事务内完成，按解析时间取候选。** `chooseTurnParent` 的候选条件是 `t.created_at_ns < 本轮 CreatedAtNS`（`graph_writer.go:437-490`）。

完整性与加密：

- **完整性事件不随 audit 删除。** 启动时按 sequence 顺序检查每个事件的 MAC 链接，再要求每条已终结 audit 有 `capture_finalized`、每个 turn 有 `semantic_compacted`（`integrity.go:143-211`）。没有 audit 行的事件可以存在，后台载荷校验会跳过它们（`integrity.go:238-248`）。所以归档后删除 audit 不需要动完整性链。
- **事件摘要绑定的是密文字节。** `semanticPayloadDigest` 对每个引用到的 content object 写入 `compression`、`encoded_length` 和 `data_enc` 的 SHA-256，对 binary object 同样处理（`integrity.go:669-696`）。密文用随机 nonce，所以拿着明文算不出原事件的摘要：归档包里的明文无法单凭原事件自证，需要归档时另行签名（4.4）。
- **子密钥由主密钥派生已有先例。** 完整性签名密钥是 `HMAC-SHA-256(主密钥, 域字符串)`（`internal/security/integrity.go:22-33`）。
- **Header 值不分凭据与否全部加密入库。** 采集层对每个 Header 值逐个加密，没有过滤（`session.go:618-655`）；Request-URI 整串加密，包含查询参数（`manager.go:219-251`）。也就是说 `Authorization`、`x-api-key` 和 `?key=` 的原值都在库里，只是密文。
- **对外输出已有一套凭据判定。** Agent 门面用 `agentapi.IsCredential` 按名称和值前缀判定，凭据值只给长度（`internal/agentapi/mask.go`）。管理员详情接口返回逐项 Header 值（模块 10）。

其他：

- **PR #54 的扩展方式是加分支。** 它在 `auditmodel.Assemble` 里加 Anthropic 的 layout，给 `Turn` 加 `SkipInlineFileData`，在 `query/turn.go` 里按 `parserName` 分派重建函数。第三个协议照此会变成三路 `if`。

### 2.2 代码梳理所得，动手前逐条复核

写入路径：

- 一条典型流式请求约 22 个 writer 操作。这是按操作类型数出来的估计，不是实测。
- writer 队列容量 1024 个操作，按个数不按字节计；`synchronous_commit=on`，语句超时 30 s。队列满不阻塞，直接返回 `ErrQueueFull`。
- 采集路径没有并发上限、没有全局内存预算，也没有任何落盘暂存。
- 解析 worker 只有一个，从库里分页读回 raw、解密、解压后再解析（`parser/evidence.go`）。轮次因此按通知顺序串行提交，`turns.created_at_ns` 是解析时间。
- 崩溃恢复依赖已经提交的 `audit_records`、`http_stages`、`body_streams` 和 `body_chunks` 行；恢复时对整张 `body_chunks` 做聚合，不带 audit 过滤（`recovery.go:82-89`）。
- 流结束时刻与终结提交的先后。草案里这一条是未证实的推断，现已由测试锁定（`internal/proxy/stream_end_order_test.go`，P0）。结论取决于响应在线路上的成帧方式，而不是它是否流式：

  | 情形 | Header 与 Body 字节 | 响应结束 |
  | --- | --- | --- |
  | HTTP/1.1 分块（SSE，或任何没有 `Content-Length` 的响应） | 先于终结提交 | 晚于终结提交 |
  | HTTP/1.1 带 `Content-Length` | 先于终结提交 | 先于终结提交 |
  | 代理自己生成的错误 JSON（上游不可达、拦截器拒绝） | 晚于终结提交，状态行也是 | 晚于终结提交 |
  | HTTP/2（SSE 和带 `Content-Length` 的响应） | 先于终结提交 | 晚于终结提交 |

  原因：Body 字节每次写入后立即 flush；分块响应的结束块由 `net/http` 在处理函数返回后写出，而处理函数被 `defer session.Finish()` 挡着；带 `Content-Length` 的 HTTP/1.1 响应，客户端收满字节数就知道结束了；HTTP/2 的 `END_STREAM` 同样等处理函数返回。“请求完成”日志也在终结提交之后才写。测试观察的是代理的直接对端（部署里是 Nginx），不是最终客户端。没有覆盖的情形：h2c、无 Body 的响应（204 或 `Content-Length: 0`）；上游返回 4xx/5xx 时走同一条拷贝路径，按其成帧方式落入上表对应行，这一点只读了代码，没有单独测试。

解析与读取：

- 只有 OpenAI 实现了 `AuditNormalizer`。Anthropic 和 Gemini 的 raw 一直是 `full`，会话另存一份在 `parsed_json_enc`。
- 流式响应的重建校验是自洽校验：`ResponseOriginal` 由同一份聚合结果构造，不与 SSE 字节比对。事件只留事件名、长度和 SHA-256，不留载荷。raw 释放后，未被聚合器消费的事件内容就没有了。
- 列表只读索引列，并逐条解密入站 User-Agent 一个字段（见 `AGENTS.md`）。详情按需从图重建。导出只有单条的（`/api/agent/v1/requests/{id}/export/{what}`），没有批量导出。

保留：

- retention 按单条 audit 的 `started_at_ns` 选取，同一会话可以只过期一部分；边界子轮次靠检查点改写成根。过期的 `audit_gaps` 按 `ended_at_ns` 单独删除。
- 派生表里，`audit_analysis`、`agent_spawn_hints` 和分析明细由解析结果重算得出，现在随 audit 一起被 retention 删除。`token_links` 来自 NewAPI，不可重算。会话分析和周报的若干表按设计比 audit 活得久。
- 没有密钥版本或轮换：密文里不带 key id（模块 09）。
- 没有 key 的请求各自成为一个 conversation（`conv_` 加 audit id）。
- 现有可复用的文件写法：`internal/agentcli/state.go` 的 `writeAtomicChecked`（临时文件、边写边算 SHA-256、提交前校验、fsync、rename）。仓库里没有 JSONL 写入器。

## 3. 目标与不变量

目标：四类协议共用一条最终落库路径；到期记录先归档、证明归档完整之后再从热库移除；归档包只凭自身和密钥就能读出全部内容。

### 3.1 已确认的决定

以下两项由维护者在 2026-11-27 确认。

**归档行写明文，压缩后整包加密。** 归档加密密钥由主密钥派生，不引入第二把需要保管的密钥。已接受的后果：

- 明文算不出原完整性事件的摘要（2.1），归档记录的防篡改依据是“归档时复核原事件”加“归档签名”（4.4）。
- 主密钥丢失时，加密的归档包同样无法打开。主密钥备份仍是唯一的关键。

**不实现恢复。** issue 里“可恢复”的意思是归档不丢东西，不是要把数据导回 PostgreSQL。因此：

- 不写恢复 CLI，不写任何从 JSONL 写回数据库的代码。issue 第 3 节和“空库恢复演练”这条验收不再适用。
- “不丢东西”由两件事保证：归档格式保留原 ID、父子关系、顺序、时间和全部内容；删除热库数据之前，证明从归档包读出的内容与热库逐项相同（4.6）。
- 归档后的数据只能用读取工具查看（4.7），回不到管理界面里。以后若要做恢复，格式里的信息是够的，但那是另一个 issue。

模块 09 和 `AGENTS.md` 里关于加密边界的表述，在实现阶段随代码一起修改，本文不改。

### 3.2 不变量

1. 转发字节路径不变。审计失败不改变已放行的请求和响应；strict 模式的起始记录语义不变。
2. 四个观察点各自的长度、SHA-256、状态、时间和缺口语义不变。只有能证明字节等价时才折叠重复数据。
3. 不完整的记录不能标成完整。
4. 崩溃耐久性的任何变化都必须是明确的决定并写进文档。现在处理函数返回时采集结果已经落库；本轮只做 4.2 的前两步，这一点不变。第三步会动到它，已定的处理方式见 5.1。
5. 已有数据继续可读，不重写全库。
6. 归档包不可变。热库的删除只发生在归档包发布、完整性核对通过、源记录未变三者都成立之后。
7. 加密开启时，明文内容不落在归档盘上：包内一切都在密文里，写入过程不产生明文临时文件。凭据值在任何配置下都不写入归档，只留名称、长度、省略标记和 keyed 指纹（4.4、5.5）。
8. 归档和移除都不改写热库里已有的完整性事件。
9. 仓库按公开信息处理：格式文档、示例和测试只用占位符。

## 4. 设计

### 4.1 协议适配统一（issue §1）

1. 并入 PR #54 的工作，作为第二个 normalizer：cherry-pick 为 P1 分支的首个提交，保留原作者归属（5.8）。
2. 把“解析、规范化、从图重建会话”收成一个按 parser 名注册的适配器接口，替换 `query/turn.go`、`parser/backfill.go`、`parser/project.go` 里的协议分支。这一步不改行为，只为第三个协议让路。
   - 落地时的一处调整：`auditmodel.Assemble` 的 layout 分支没有改成注册，而是改成 `auditmodel` 包内的一张数据表（每个 layout 一行，写明各 slot 是数组、恰好一个、至多一个还是没有）。原因是已存的 layout 必须能被任何读取方装配，包括只用 `auditmodel`、不引入任何 parser 的离线导入校验、两个存储的测试和以后的归档读取工具；靠注册的话，漏掉一个 import 就会在第一次重建时才报“不支持的 layout”。适配器只声明自己会写出哪些 layout，注册表在进程启动时校验它们都在表里。新增一个 layout 是表里加一行，再在适配器里声明。
   - 注册表是 `internal/parser/builtin` 里一份显式的列表，包初始化时构建并校验，列表有错进程起不来。没有 `init()` 注册，也没有可变的全局状态。
3. 新增 Gemini normalizer，覆盖 GenerateContent 与 StreamGenerateContent。请求按 `contents[]` 逐条成 item，`systemInstruction` 比照 #54 的 system 处理。会话 key 的来源需要先调查客户端实际发什么，没有可靠 key 时走无 key 的内容推断。
4. **流式内容不丢是释放 raw 的前提。** 每个协议定义“已消费事件类型”清单。一条流里只要出现清单外的事件、聚合器没有读走的字段，或聚合结果覆盖不了的内容（工具调用、用量、签名、引用、多模态、扩展字段），就把这些事件的载荷作为 content object 挂在响应 envelope 上；单条超过上限时整条升级为 `full`。
5. 每个协议配一组保真夹具：同一份 SSE 字节，分别从 raw 和从图重建两条路径导出会话、用量、工具调用和停止原因，结果必须相同。没有通过这组夹具的协议不允许进入 `metadata`。
6. 流式响应的 envelope 不再为每个 SSE 事件存一个 SHA-256，改成紧凑描述：事件名的游程编码、长度序列，加一个覆盖全部事件的哈希（附录 A.3 第 5 项）。这是新的 layout 版本，与第 4 条的未消费事件规则一起设计；旧 layout 的行按原方式读取。
7. raw 的保留按侧决定：请求侧和响应侧各自判断走重建还是保留原文，规则见 5.9。它改的是证据保留规则，模块 18 同步更新。

parser 版本各自递增。旧版本写入的行按原方式读取。

这一节和归档直接相关：raw 一旦在热库里被释放，归档能留下的就只有规范化后的内容。规范化丢了什么，归档就丢了什么。

### 4.2 热写路径（issue §1）

分三步做，每一步都能单独量、单独回退。前两步不改变耐久性。**本轮只做第一步和第二步**；第三步以这两步的 A/B 实测为门禁，由维护者决定是否需要，做法见 5.1。

**第一步：终结时一次提交。** 把 `StartStage`、`AddHeaders`、`StartBody`、`AddChunk`、`FinishStage`、`FinishAudit` 合成一个 `CommitAudit` 操作，在 `Finish` 时一次提交：一个 savepoint，块用多行插入。处理函数照旧等这次提交。raw 仍然写库。成对阶段的等价判断挪到提交之前在内存里完成，重复的那一份不再先写后删。

Header 的写入随这一步重写（5.10）：四个阶段的 Header 和 Trailer 合并成每条 audit 一个压缩加密块，入站 User-Agent 另存独立的 `user_agent_enc` 列；`audit_records` 新增 `capture_version`，新数据用 `capturePayloadDigest` v2，旧行按 v1 校验。

**第二步：解析不读回。** 终结器拿内存里的明文 Body 直接解析、规范化、`Prepare`（对象查重走只读连接），省掉分页读回、解密和解压。`SaveParsedAudit` 仍是独立事务，raw 仍然先写后删。

**第三步：规范化先于提交。** 解析和规范化在提交之前完成，`CommitAudit` 一个事务写完终态、四个阶段、Header、`body_streams`、时间线、`parsed_results`、turn 图和对象。只有保留级别为 `full` 的记录才写 `body_chunks`。`capture_finalized` 和 `semantic_compacted` 在同一事务里按原顺序追加，事件格式和校验规则不变。这一步让处理函数要么多等一段解析时间，要么不再等提交。本轮不做；是否做、怎么做按 5.1。

三步共用的规则：

- **内存里存明文。** 会话持有各阶段的明文 Body，预算按明文字节计，分单请求和全局两级。gzip 与 AES 只在两种情况下发生：写 `full` 记录的 `body_chunks`，或者落暂存。普通成功请求在第三步之后不再为 raw 付压缩和加密的开销。
- **成对阶段增量比对。** 后一阶段观察到的字节与前一阶段同偏移的字节逐片比较，相等时后一阶段只记长度和哈希。出现分歧或后一阶段提前结束时，按现有 `body_stage_mismatch` 语义保留两份。
- **暂存。** 第一步把块攒到终结时一次提交，超出内存预算的大 Body 怎么处理，决策评论没有覆盖。实现前就此问过维护者，答复是落本地暂存，不沿用边转发边写库。超出预算的请求把后续内容密封成现有格式的 AES-GCM 块（AAD 不变），追加到本地暂存文件，内存只留索引；终结器处理这类请求时从暂存读回。暂存目录由配置指定，权限 0700，文件 0600。启动恢复扫描暂存目录，把遗留块作为 `partial`、`process_exit`、`full` 证据导入后清掉文件。落暂存时同步保存已经启动的阶段的 Header，保证崩溃恢复能拼出残缺的 Header 块（5.10）。
- **耗尽。** 预算和暂存都满时，按现在队列满的语义处理：该阶段标 `partial` 并记 gap，available 模式继续转发。
- **回退。** 终结器失败、超时或 panic 时，提交采集结果，raw 记 `full`，`parse_status=pending`，由现有异步解析 worker 接手。现有路径同时继续服务回填和启动恢复。
- **顺序。** 首版只起一个终结器，按 `Finish` 的交接顺序处理并提交，与现在单个解析 worker 的顺序保证相同：同一会话的后一轮不会先于前一轮提交，父轮次推断不会因为乱序把后一轮错判成新根。并行终结要等压测证明单个终结器是瓶颈之后再做，并且必须按交接序号重排，提交顺序仍等于交接顺序。
- **起始记录。** `BeginAudit` 在 strict 和 available 两种模式下都永久保持同步提交（5.6）。
- **开关。** 配置项 `audit.write_path` 取 `legacy` 或 `unified`，默认 `legacy`。两条路径写出的行可以共存。
  （2026-11-28 补记：第 3 阶段 A/B 之后维护者决定只保留 unified，legacy 写入路径已删去，这个开关不再选择任何东西：省略或写 `unified` 照常启动，写 `legacy` 时配置校验失败。旧的版本 1 行照常读取和校验。回滚只能换回上一个版本的二进制，不含迁移 007 的版本读不了采集版本 2 的行。见第 3 阶段设计实施记录 R.8。）

### 4.3 读取侧（issue §1）

- **列表**：现在已经只读索引列和一个 User-Agent 字段。本方案不改，只在 A/B 里确认规范化统一后没有新增读取。
- **详情**：照旧按需从图重建，分派改走 4.1 的适配器。
- **批量导出**：现在没有，是新增项。做一个按会话分组的读取器：同一会话的轮次共用祖先引用和已解码对象的有界缓存，共享的历史对象只读一次、只解密一次。`integrity.go` 里的 `integrityGraphCache` 是现成的先例。这个读取器同时给会话导出接口和归档写入器用。

### 4.4 归档格式（issue §2）

**归档单位与分段**

- 每行一条 audit，也就是一轮对话。
- 到期按单条 audit 的 `started_at_ns` 判断，与现在的 retention 相同（5.2）。归档每天运行一次，时刻按本地时区配置，默认 `03:00`。
- 到期记录按 `conversation_id` 分组。单次到期量达到阈值的会话，一组写成一个独立分段；低于阈值的会话和没有 turn 的 audit 装进当次运行的桶包，按协议分（5.3）。
- 分段和桶包都按大小滚动：超过 `archive.segment_max_bytes` 时在同一次运行里切成连续的多个。
- 会话在归档后又出现新轮次时，新轮次进入下一个分段或桶包，旧包不动。所以同一个会话可能同时分布在独立包和桶包里。

**文件**

```text
<archive_dir>/
  gaps/gaps-<first_id>-<last_id>.jsonl.gz.enc
  sessions/<YYYY>/<MM>/
    <created_utc>_<last_active_utc>_<conversation_id>_s<NNNN>.jsonl.gz.enc
    <created_utc>_<last_active_utc>_bucket-<protocol>_s<NNNN>.jsonl.gz.enc
    <同名>.objects.jsonl.gz.enc
    <同名>.manifest.json
```

- 加密开启（默认）时扩展名是 `.jsonl.gz.enc`；关闭时是 issue 里写的 `.jsonl.gz`。
- 文件名里的两个时间取包内 audit 的 `started_at_ns` 最小值和 `ended_at_ns` 最大值，UTC。不用 `conversations.created_at_ns`，那是解析时间。两个时间同时写进清单和行内。
- 桶包的文件名里没有会话 ID，用 `bucket-<protocol>` 占位；具体写法在 P3 的格式文档里定稿。文件名只供人看，不是查找依据。
- 对象集为空的包不产生 `.objects` 文件，清单里对象数为 0。
- `manifest.json` 是明文，只放不含内容的字段：归档格式版本、来源库迁移版本、`bundle_kind`（`"conversation"` 或 `"bucket"`）、成员会话列表 `conversations[]`、各表的列清单、归档密钥指纹、各文件落盘字节的大小和 SHA-256、行数、对象数、成员 audit 及各自的记录摘要和修订号，以及对上述全部内容的签名。不拿密钥也能核对文件是否完整。读取工具靠清单建索引来定位会话，不靠文件名通配（4.7）。

（2026-11-28 补记：实际的文件名带写出它的运行 id 的前 8 位：会话包是 `<最早开始>_<最晚结束>_<conversation_id>-<run8>_s<NNNN>`，桶包是 `…_bucket-<protocol>-<run8>_s<NNNN>`，gap 包是 `gaps/gaps-<first_id>-<last_id>-<run8>`；同一批记录在后来的运行里以更高的修订号重新导出时，靠它与旧包区分。会话 id 不能放进文件名的会话进桶包。见第 4 阶段设计实施记录 R.5 第 1 条与[模块 26](../features/26-cold-archive.md) §3。）

**行内容**

每行一个版本化的 JSON 对象，是该 audit 在各表里的行，密文列解密后写出：

- `audit_records`（含 Request-URI）、`http_stages`、`http_headers`、`body_streams`、`stream_timelines`、`parsed_results`（含解析结果 JSON）、`token_links`、`turns`、`turn_response_items`、`audit_project_identity`（有则带）。
- 请求上下文：父轮次在同一分段里时存原样的增量操作；父轮次不在本分段时存物化后的完整引用。原始的 `parent_turn_id`、`parent_base`、`link_reason` 作为血缘信息单独保留。这样单个分段不依赖其他包、也不依赖热库，就能读出每一轮的完整上下文。
- 该 audit 的原完整性事件（sequence、类型、两个 MAC、载荷摘要、时间），作为历史记录。
- 行尾是记录摘要。

`objects` 伴随文件存放本分段引用到的对象，每个只存一次：content object 的规范化 JSON、binary object 的原始字节（base64）、对象的外部引用，以及 `full` 记录各阶段的 raw 字节。对象放在每个包里，包自足；只有 P0 量出的膨胀比超过界限时才改用按月作用域的共享对象库（5.4）。

可重算的派生数据（`audit_analysis`、`agent_spawn_hints`、分析明细）不进归档。

编码规则：

- 64 位整数和纳秒时间戳一律写成十进制字符串。
- 非 UTF-8 的字节内容写 base64，并标明编码。
- 行首重复 `audit_id`、`conversation_id`、协议、起止时间几个字段方便检索；它们必须与行内各表一致，校验时比对。

**记录摘要**

记录摘要定义在明文上，与密钥、nonce、压缩结果都无关：

- 覆盖范围比照现有的 `capture_finalized` 与 `semantic_compacted` 两个摘要的字段集合，把其中“密文的 SHA-256”换成“明文的 SHA-256”，再补上这两个摘要没有覆盖、但归档行里有的列。
- 对象只取内容地址：content object 取 `object_hash`、语义哈希、kind、明文长度，binary object 取 `binary_hash` 和长度。内容地址本身就是对明文的哈希。
- 同一条记录在源库和归档包里算出的摘要相同。重读校验、“源记录在归档后是否变过”和修订号都以它为准。

**签名**

- 归档器在同一个快照里先对每条成员复核原完整性事件：按现有规则重算载荷摘要并验证 MAC。复核不过的 audit 不归档、不删除，留在热库并给出稳定的 `archive_integrity_failed` 状态。
- 复核通过后，清单用归档签名密钥做 HMAC。签名的含义是：这些明文对应的行，在归档那一刻通过了原完整性校验。
- 归档加密密钥和归档签名密钥各用一个域字符串从主密钥派生，互相独立，也独立于完整性签名密钥。清单里的密钥指纹由归档密钥算出，读取前先比对。

**整包加密**

- 写入顺序是 JSONL → gzip → 加密 → 归档盘上的临时文件 → rename。明文和未加密的压缩流只存在于内存管道里，不落盘。
- 加密格式的要求：分帧的认证加密；每帧独立认证；帧序号和末帧标记参与认证，截断、重排、拼接都能检出；文件头带格式版本和随机盐。用现成的库还是在仓库内实现，留到 P3 决定，两者都要配固定的测试向量。
- `archive.encrypt` 默认开启。关闭时文件是普通的 `.jsonl.gz`，可以直接用 `zcat` 读。

**凭据值**

库里现在存着 `Authorization`、`x-api-key`、`?key=` 这类凭据的原值（2.1）。明文行必须对它们单独定规则，判定沿用 `agentapi.IsCredential`，同样适用于 Request-URI 的查询参数：

- 无论加密开启还是关闭，凭据值一律不写入（5.5）。凭据项只留 `name`、`length`、`value_omitted: "credential"` 和 `value_fpr`。这是归档里唯一允许缺内容的地方。
- `value_fpr` 是用归档子密钥对原值算出的 keyed 指纹。同一个值在入站和出站阶段得到相同的指纹，可以证明两侧凭据一致；持有密钥的人可以拿一个已知的 Key 算指纹来核对归属。指纹密钥用独立的域字符串从主密钥派生。
- 加密包与非加密包的行 schema 和记录摘要完全相同。
- 读取工具输出的就是这个脱敏后的形式，没有输出原值的参数，因为包里没有原值。
- 记录摘要按写入归档的形式计算：凭据项以名称、长度、省略标记和指纹参与摘要。热库一侧算记录摘要时先做同样的脱敏投影，两边才可比。

**进程级 gap**

`audit_gaps` 不属于任何 audit，现在由 retention 直接删。归档开启后，过期的 gap 先导出到 `gaps/` 再删。

**格式兼容策略**

- 承诺：任何正式发布过的归档格式版本，当前及以后的读取工具都能读。
- 手段：清单自带各表列清单，所以库表以后加列、改列不影响旧包的解读；每个已发布的格式版本留一份冻结的夹具包，CI 里用当前的读取工具逐个读一遍。
- 格式文档随代码一起发布，写到不依赖本仓库代码也能解析的程度。
- 在 P3 的完整性验收通过之前，格式版本标为 0（试行）。试行包不作为删除热库数据的依据，格式改动后需要重新导出。

### 4.5 归档、校验、移除（issue §2）

配置 `archive.mode` 三态：`off`、`export_only`、`archive_then_delete`。

一次运行的步骤：

1. 用只读连接在 REPEATABLE READ 快照里选出到期记录并分组，读出各表的行并解密，算出记录摘要，复核原完整性事件（4.4）。不占用 writer。解密本身也顺带验证了每段密文的 AEAD，损坏的记录在这里就会被拦下。
2. 按 4.4 的顺序流式写入临时文件，边写边算落盘字节的 SHA-256；fsync 后写清单并签名、fsync，rename 发布，再 fsync 目录。
3. 重新打开已发布的文件做完整性核对（4.6）。
4. 在热库登记目录表：分段、成员 audit、记录摘要、变更戳、状态 `sealed`。
5. `archive_then_delete` 模式下，用独立的小事务移除：事务内对每条成员比对变更戳，一致才删。删除本身复用现有的检查点、叶到根删除和对象 GC，只是输入从“按截止时间选”换成“给定 id 列表”。id 列表按 `turns.created_at_ns` 降序切批，子先于父（5.2）。批量与让路沿用 PR #55 的逻辑。
6. 标记分段为 `hot_removed`。

（2026-11-28 补记：实际的顺序是先登记、后发布：写完并 fsync 临时文件和签名的清单，在目录表登记 `publishing` 的意向（成员、记录摘要、变更戳），再以硬链接发布、重读核对、抽样比对，最后改为 `sealed`。这样崩溃后变更戳始终在库里，对账只需要看文件在不在。变更戳也不是上面的字段清单，而是各表行的主键加 `xmin`。见第 4 阶段设计 Q1、Q12、H.2 与实施记录 R.5、R.6、R.8。第 5、6 步的移除还没有上线。）

变更戳是一组不含密文的小字段，能在 writer 事务里靠索引读出，不破坏 PR #55 的一秒目标：`audit_records` 的解析状态与调用者关联状态及更新时间、`parsed_results.parsed_at_ns`、`token_links` 的条数与最大 `linked_at_ns`、各阶段的 `retention_state`、turn 的父引用。P3 要先枚举所有会 UPDATE 已归档表的语句，确认变更戳覆盖了它们。

失败处理：

- 磁盘满或写入失败：删掉临时文件，不登记、不删除，退避重试，并给出稳定的 `archive_failed` 状态。启用归档后，任何情况下都不会跳过归档直接删。
- 发布之后、登记之前崩溃：下次运行先对账归档目录，把核对通过但未登记的包补登记。
- 登记之后、删除之前崩溃：下次运行从第 5 步继续。
- 源记录在归档后发生变化（例如迟到的调用者关联）：该成员不删，标记 `stale`，下一个分段以更高的修订号重新收录。读取时同一 audit 取最高修订号。
- 归档期间会话继续活跃：新轮次不在快照里，也没到期，不受影响；删除时它若引用了被删的父轮次，由检查点处理。

归档目录表需要一个新的迁移版本。它不是本方案唯一的库表改动：P0b 删除一个索引，P2 给 `audit_records` 加 `capture_version` 和 `user_agent_enc` 并引入单一 Header 块（5.10）。各项按落地顺序依次取号，清单见第 6 节。每个新版本都有同样的后果，要写进部署说明：旧版本遇到更新的库打不开审计存储（进程照常起来，`available` 模式不留 audit 照常转发，`strict` 模式回 `503`；草案里写的“拒绝启动”不准确，P0b 对照代码和既有测试更正）；离线导入器和 `audit-stage` 的白名单要同步更新，否则会拒绝目标库。目录表是管理数据，不进完整性链。

配置与启动时的护栏（5.7）：

- `archive.mode` 默认 `off`，此时 retention 维持现有的直接删除。
- 配置校验拒绝 `archive.mode != "off"` 而 `retention_days == 0`；拒绝 `archive.dir` 与 `key_path` 位于同一目录或互相包含。
- `export_only` 模式不做任何直接删除，启动日志提示热库会持续增长。
- 从 `archive_then_delete` 切回 `off` 而 `retention_days > 0` 时，启动日志醒目提示直接删除已经恢复；暂停归档的正确做法是把 `retention_days` 设为 0。
- `HasAudits` 同时检查 `audit_records`、`integrity_events` 和归档目录表，三者都为空才允许新建密钥。

热库查询不读归档。已归档的会话在界面里不可见，只能用 4.7 的读取工具查看。

### 4.6 证明归档不丢东西

不做恢复以后，“归档完整”不能靠导回数据库来验证，要在删除之前直接证明。分三层：

**列覆盖。** 一条测试从库表定义里列出所有被归档表的全部列。每一列要么出现在归档行里并进入记录摘要，要么在一份显式的排除清单上并写明理由。以后的迁移给这些表加了列却没更新归档格式，这条测试就会失败。它防的是“新加的字段悄悄没进归档”。

**数据一致。** 每次运行的重读校验（4.5 第 3 步）对每条成员做：

- 验清单签名和文件哈希，解密、解压、逐行解析，核对行数。
- 从包内的行重算记录摘要，与第 1 步从热库算出的值比对。
- 重算每个对象的内容地址；`full` 记录的 raw 字节对回 `body_streams` 里记的 SHA-256 和长度。
- 引用闭合：行里引用的每个对象都能在本包的 `objects` 文件里找到；父轮次不在本分段的轮次都带着物化后的完整引用。包内没有任何指向热库的引用。

任何一项不过，该包作废，成员不登记、不删除。

**读出等价。** 只凭归档包，读取工具导出的会话、provider 请求与响应 JSON、Header、时间线和 raw，与查询层从热库对同一条记录给出的结果逐项相同。比对统一经过 4.4 的凭据脱敏投影：热库一侧的输出先把凭据值换成名称、长度、省略标记和指纹，再与归档一侧比（5.5）。这证明的是格式可解读，不只是字节都在：

- 测试里对四类协议的全部夹具做全量比对。
- 运行时按 `archive.verify_sample` 配置的比例抽样比对，默认每个包至少一条。抽样不过同样作废该包。

**归档里的完整性证据。** 热库的完整性链不受影响，被归档 audit 的原事件继续留在链里。归档行里带着这些事件的副本，清单签名说明它们在归档那一刻复核通过。

### 4.7 读取工具

新增 `cmd/audit-archive`，只读归档目录，不连数据库：

- `verify`：对一个包或整个目录做 4.6 里“数据一致”那一层的检查（与热库比对的部分除外）。
- `list`：按清单列出包、会话和时间范围。不需要密钥。
- `cat`：解密后把明文 JSONL 写到标准输出，可按会话或 audit 过滤。包里没有凭据值，输出里也没有。
- `export`：把一个会话或一条 audit 导出成现有单条导出的那几种形态（会话 JSON、provider JSON、raw、时间线）。

按会话或 audit 查找时，工具先读目录下全部明文 `manifest.json` 建索引，再打开命中的包。不靠文件名通配：同一个会话可能分布在多个独立包和桶包里（5.3）。

`verify` 的解密部分、`cat` 和 `export` 需要主密钥文件。这个工具就是 issue 里“可独立读取”的落点：有归档目录和密钥，不需要原来的 PostgreSQL 也不需要运行代理，就能读出全部内容。

## 5. 已定决策

以下十项在草案第四版里是待定项，维护者已在 issue #59 上逐项定论。每项保留当时列出的选项，随后写结论、理由和补充要求。实现与本节冲突时以本节为准；本节没有覆盖、而实现中必须做的取舍，尤其是证据语义和完整性格式上的，先问维护者。

### 5.1 交接时的耐久性（决定 4.2 第三步）

现在处理函数返回时采集结果已经落库。规范化挪到提交之前以后，有三种做法：

- 甲，处理函数等到 `CommitAudit` 提交。耐久性不变，但处理函数要多等解析和规范化的时间，上下文越长等得越久。
- 乙，交接前把证据密封写入暂存并 fsync，处理函数随即返回；崩溃后由暂存重放。
- 丙，交接后立即返回，不落暂存。从交接到提交之间崩溃，会丢掉一条客户端已经完整收到的请求的证据，库里只剩起始记录。这比现在弱。

**结论：否决乙。本轮只做 4.2 的第一步和第二步；第三步以这两步的 A/B 实测为门禁，不提前承诺。**

- 否决乙的理由：它要求每条 2xx 请求在返回前密封并做一次本地 fsync，与 4.2“普通成功请求不再为 raw 付压缩和加密开销”矛盾；丢掉 PostgreSQL 批提交的优势；要维护两套崩溃重放语义（在途溢出的残缺证据，和已经 `Finish` 的完整终态）；并且与 `compose.yaml` 的 `read_only: true` 加单个 `/data` 密钥卷的部署形态冲突。
- 如果 A/B 证明仍然需要第三步：优先评估甲的并发变体，即 `NormalizeAudit` 与 `PrepareWithLookup` 并发执行，只有 `chooseTurnParent` 和 `CommitAudit` 按交接顺序提交。它不降低崩溃耐久性，也不改变 `llm request completed` 日志的语义，作为默认模式。
- 丙只作为显式的低延迟可选项，并且必须搭配同步的 `BeginAudit`（5.6）。

### 5.2 到期按单条 audit 还是按会话

- 甲，按单条 audit，与现在的 retention 相同，也是 issue 的字面要求（“符合保留策略的终态记录”）。归档运行改为每天一次，一个会话每个活跃日最多产生一个分段。代价是跨天的会话有多个分段，每个分段的边界轮次都要带一份完整的上下文引用。
- 乙，按会话：最后一次活动早于截止时间才整段归档。代价是 `retention_days` 的含义变了，与 `archive.mode=off` 时的行为不一致，还要为长期复用同一个 key 的会话另设上限。

**结论：甲，按单条 audit，每天运行一次。** 保留策略的语义在归档开关两侧保持一致；热库的实际保留时间是 `retention_days` 加最多一天。补充两项要求：

1. 归档运行时刻可以配置为本地低峰时间，复用 `session_analysis.run_at` 加 `timezone` 的配置模式，默认 `03:00`。不按 UTC 0 点切，避免把单日会话在白天工作时段拦腰切成两段。
2. P4 按 id 列表分批删除时，按 `turns.created_at_ns` 降序切批，也就是拓扑上叶到根、子先于父。不能按 `started_at_ns` 降序，因为父子关系是按解析顺序建立的。顺序不对时，自适应缩批会反复触发 `checkpointRetainedChildren` 的重写，代价随批数平方增长。

### 5.3 小会话与无 turn 记录怎么装包

没有 key 的请求各自是一个 conversation，没有 turn 的 audit（被拦截、失败、不完整、解析失败）不属于任何会话。一会话一包会让它们各自产生三个小文件。

**结论：按阈值加协议装桶包。** 单次到期量低于阈值的会话，连同无 turn 的 audit，装进当次运行的桶包（按协议分，按大小滚动），清单里列出成员会话；达到阈值的会话独立成包。具体的轮次和字节阈值由 P0 量出的“每个 conversation 的轮次数和字节数分布”决定。补充规范（已写入 4.4、4.7）：

- 清单增加 `bundle_kind`（`"conversation"` 或 `"bucket"`）和 `conversations[]`；对象集为空时不产生 `.objects` 文件。
- `audit-archive` 按明文 `manifest.json` 建索引来定位会话，禁止靠文件名通配查找：跨天的会话可能同时分布在桶包和独立包里。

### 5.4 对象放在包内还是共享对象库

- 包内：每个包自足，可以单独拷走、单独读取、单独销毁。代价是跨会话共享的对象（系统提示、工具定义）每个包重复一份，跨天会话的每个分段也重复一份上下文。
- 共享库：全归档去重。代价是包不再自足，销毁某个包需要对对象库做可达性清理，丢了对象库所有包都读不全。

**结论：包内自足，由 P0 实测的膨胀比兜底。** 只有当 P0 量出“各包去重后对象字节之和”与“全局去重后对象字节”之比超过 3 到 5 倍时，才改用按月作用域的共享对象库（`sessions/<YYYY>/<MM>/objects/`），保证旧月份仍然可以直接按目录删除。不做全局共享库，也不做归档 GC。

### 5.5 归档包内是否保留凭据值

- 保留：归档与热库逐项相同。包内的保护强度与数据库相同，都系于主密钥。
- 不保留：归档盘上任何形式都不含 API Key，哪怕主密钥泄露。代价是归档比热库少了这些值。

**结论：不保留。加密开启与关闭一律省略凭据值。** 草案第四版“加密包内保留”的建议不采纳。具体规则：

- 判定复用 `agentapi.IsCredential` 和 Request-URI 查询参数的掩码规则。凭据项只保留 `name`、`length` 和 `value_omitted: "credential"`。
- 另附一个由归档子密钥派生的 keyed 指纹 `value_fpr`。它既能证明入站与出站阶段的凭据一致，也能在本地拦截、`401`，或没有 `X-Oneapi-Request-Id`（`token_links` 为空）的记录上，支持拿一个已知的 Key 核对归属。
- 加密包与非加密包使用同一套 schema 和同一个记录摘要。4.6 的读出等价校验统一经过这个脱敏投影来比对。
- 如果以后确有单人取证场景需要原值，最多作为默认关闭的 `archive.include_credentials` 另行提出，不在本轮范围内。

### 5.6 available 模式的 BeginAudit 是否保持同步

**结论：永久保持同步。** 本地 PostgreSQL 上这一步约 5 到 7 ms，相对 LLM 的首字延迟可以忽略。`RecoverInterruptedAudits` 完全依赖 `ended_at_ns IS NULL` 的起始行来发现崩溃时的在途请求，它也是 5.1 丙的安全兜底。如果 A/B 显示批等待偏高，优先调低 `writerBatchDelay`，不改成异步。

### 5.7 归档关闭时 retention 做什么

**结论：`archive.mode` 默认 `off`，保持现有的直接删除行为；归档是显式开启的能力。** 随 P3、P4 补齐五条安全护栏：

1. 配置校验拒绝 `archive.mode != "off"` 而 `retention_days == 0` 的组合。
2. `export_only` 模式明确禁止直接删除，并在启动日志里提示热库会持续增长。
3. 回滚文档和启动日志醒目提示：从 `archive_then_delete` 切回 `off` 而 `retention_days > 0` 时，会立刻恢复没有归档的直接删除。想暂停归档应当把 `retention_days` 设为 0。
4. 配置校验禁止 `archive.dir` 与 `key_path` 位于同一目录或互相包含，把“密钥与归档目录分离”做成硬约束。
5. 修复 `HasAudits` 的判定：同时检查 `audit_records`、`integrity_events` 和归档目录表。否则热库被归档清空以后，如果密钥文件缺失，启动会误新建密钥并破坏既有的完整性链。

- 乙，不合入，把它的改动搬进本 issue 的分支，直接按注册接口重写。

**结论：两者都不采用。PR #54（提交 `b6e67be`）cherry-pick 为 P1 分支的首个提交，不随生产版本先行发布它现在的 v3。** 保留原作者的提交归属、测试，以及 `SkipInlineFileData`、`messages` 先于 `system` 这类细节修复。在同一个 P1 阶段里补齐适配器注册表、4.1 第 4 条的未消费事件保真（保住 `signature_delta`、`citations_delta`）和紧凑 SSE 描述（附录 A.3 第 5 项），然后再合并发布；或者先合入 `main` 但在 P1 合入前不发版。

### 5.9 异常请求是否只保留响应侧的 raw

模块 18 §6 原来的规则是：结果只要异常（非 2xx/3xx、转发或采集不完整、解析不完整），四个阶段的 raw 全部保留。实测里这条规则占了库的 38%，而其中 98% 是请求体，绝大多数请求体本身完整无误，出问题的只是响应（附录 A.3）。

- 甲，维持现状。
- 乙，按侧决定：请求侧规范化并通过重建校验后释放请求 raw，只保留响应侧 raw。请求侧的证据从“逐字节原文”变成“内容对象加重建哈希”，与正常请求现在得到的保证相同。

**结论：乙，按侧决定保留，同步更新模块 18。** 它不依赖 4.2，排在 P1 之后。补充以下规则和必须修的代码缺口：

1. **4xx 细分。** `5xx`、`429`、`401`、`403`、`408`、`409`、`499`、客户端中途取消，以及响应解析不完整的记录：请求侧规范化和重建校验通过，并且 `request_sent.source_stage == request_received`（没有 `body_stage_mismatch`）时，释放请求 raw，只留响应侧 raw。只有 `upstream_error_class IS NULL` 的 `400` 和 `422`，以及请求解析失败、校验失败或超限的记录，保留请求侧的 `full` raw。这样 `429` 重试风暴不会打爆空间，畸形请求的取证能力也保住了。上面没有列出的状态码（`402`、`404`、`405`、`413`、`415` 等其他非 2xx/3xx）保留请求 raw；实现时就此问过维护者，答复是保留。
2. **残缺响应不丢内容。** 有 turn 以后 `parsed_json_enc` 默认不再存 `conversation`，而 `LayoutNone` 的重建只输出请求消息。残缺的响应消息不能直接写回 `parsed_json_enc.conversation`：`query/service.go` 的 `validConversation` 会校验索引连续，写回去会得到 `500 ErrIntegrity`。在 `parsed_json_enc` 里用独立的键 `partial_response_messages` 只保存响应侧的半截消息，详情、会话导出、回填和归档读取时统一合并并重排 `Index`。
3. **下游按侧支持。**
   - `internal/parser/backfill.go` 的 `backfillInput` 改为请求、响应分别判断走重建还是读 raw，不再只看 `StageRequestReceived`。
   - `internal/web/api.go` 的 `serveReconstructed`、`internal/web/agent_requests.go` 的 `agentExportStates` 和前端 `TurnStoragePanel` 正确处理 `ResponseLayout == LayoutNone`：标 `not_available`，不返回 `200 null`。
4. **对现有数据做原地回收的前提（纠正草案第四版附录 A.3 的一处错误）。** `postgres/integrity.go` 的 `reconstructionFailurePayloadDigest` 同时覆盖 `parsed_results.parsed_json_enc` 和 `body_streams.retention_state`，这两列并非“不在任何摘要里”。原地回收必须跳过存在 `semantic_compacted` 或 `reconstruction_failed` 完整性事件的记录，只处理只有 `capture_finalized` 的记录。

### 5.10 Header 的存储形式

现在每个 Header 值一行、各自加密。实测每条请求 52 行，表加主键索引占库的 10%；发往上游的 Header 与收到的几乎逐条相同（附录 A.3）。

- 甲，维持现状。
- 乙，成对阶段去重：后一阶段只存与前一阶段的差异。行数减半。
- 丙，每个阶段的 Header 合成一个压缩后加密的块，再做成对去重。

**结论：淘汰乙，采纳改良后的丙，随 4.2 第一步落地。** 相对草案第四版有以下修正：

1. **存储结构。** 不按阶段分块，也不做手工的成对 diff 和墓碑。每条 audit 在 `CommitAudit` 时把四个阶段的 Header 和 Trailer 合并成单一的压缩加密块。四个阶段合计只有几 KB，都在 gzip 的 32 KiB 窗口内，跨阶段的重复由压缩自动消除，逻辑最简单，体积约降 90%。
2. **强制独立的 `user_agent_enc` 列。** 草案里“或者从块里取”的选项去掉。
   - 守住 `AGENTS.md` 和模块 09 的边界：列表页只解密 `User-Agent`，不读取其他敏感 Header。同时消除 `List` 现有的 N+1 查询。
   - `user_agent_enc` 纳入 `capturePayloadDigest` v2，防篡改。
   - 保真 `NULL`（缺失）与 `""`（空串）的区别，以及多值有序 `[]string` 的子串筛选语义。
3. **读路径与恢复。**
   - `LoadParserStage` 对 `metadata` 记录不读取、不解密 Header 块，避免回填扫描误解密敏感 Header；需要的非敏感字段 `content_type`、`content_encoding` 放在 `http_stages` 或 `body_streams` 上。同步更新模块 23。
   - 超限落本地暂存时，同步保存已经启动的阶段的 Header，保证崩溃恢复能拼出残缺的 Header 块。
4. **摘要版本。** `integrity_events` 没有版本列。在 `audit_records` 上新增 `capture_version BIGINT NOT NULL DEFAULT 1`，不改动 `integrity_events`；`capturePayloadDigest` v2 只对新数据生效，旧行按 v1 校验。

## 7. 验证

**共用热写路径**

- 四类协议、流式与非流式各一组拟真数据；覆盖多轮与分支、工具与多模态、未知事件、断流与取消、错误响应、进程崩溃、并发内存压力。
- `legacy` 与 `unified` 两条路径跑同一组输入，比对转发字节、已有记录读取、详情和导出，结果必须相同。
- 故障注入沿用现有手段（只读事务、触发器抛指定 SQLSTATE、延迟外键、容量为 1 的队列），新增暂存目录写满、暂存文件损坏、终结器 panic、预算耗尽、交接后提交前崩溃。
- 顺序测试：同一会话的两轮紧挨着结束，验证后一轮挂在前一轮之下。

**PostgreSQL A/B**

同一工作负载下记录：每条 audit 的提交数（`pg_stat_database`）、写入行数与删除行数（`pg_stat_user_tables`）、WAL 字节（LSN 差值）、堆与 TOAST 大小、进程内存峰值与暂存字节、首字节延迟、流结束延迟、结束到可查询延迟、详情与导出的 p95。先留基线再定门槛。去重率单独报告，不作为提速的证据。

**归档完整性**

- 列覆盖测试通过，并用“给被归档的表加一列”验证它确实会失败。
- 四类协议的全部夹具：只凭归档包，读取工具导出的会话、provider JSON、Header、时间线和 raw 与查询层从热库给出的结果逐项相同。旧格式的行（`parsed_json_enc` 加 `full` raw）同样覆盖。
- 跨分段的会话：父轮次在更早的分段里、甚至那个分段已经不在时，后一个分段仍能单独读出完整上下文。
- 加密包被截断、帧被重排、清单被改动、对象文件缺一个对象时，核对和 `verify` 都能检出。
- 原完整性事件复核不过的 audit 不进归档，仍留在热库。
- 扫描归档目录和写入过程中的临时文件：加密开启时扫不到任何测试正文；加密开启与关闭两种配置下都扫不到凭据值。
- 凭据指纹：同一个凭据在入站和出站阶段的 `value_fpr` 相同；拿已知的 Key 和归档子密钥能算出同一个指纹；换一把主密钥算不出。
- 对每个已发布格式版本的冻结夹具包，用当前的读取工具读一遍。

**移除**

- 磁盘满、包损坏、归档后删除前崩溃、重复执行，都不丢数据；重试幂等。
- 源记录在归档后变化时不删除，并在下一分段以新修订号出现。
- 归档期间会话继续活跃：热库里仍被引用的边界轮次靠检查点保留，剩余会话查询正常。
- 删除之后，热库的完整性链校验和后台载荷校验照常通过。

依赖 PostgreSQL 的测试在没有 DSN 时会被跳过。验收报告里要分别写明哪些在真实库上跑过。

## 8. 风险与回滚

- **没有恢复路径。** 归档并删除之后，数据回不到管理界面，也不能再参与洞察、周报这类统计，只能用读取工具查看。启用 `archive_then_delete` 之前要让使用者清楚这一点。格式保留了以后做恢复所需的信息，但没有任何代码验证过这条路。
- **“不丢东西”靠的是检查，不是往返。** 4.6 的三层检查覆盖了能想到的丢失方式，但它证明的是“归档包与热库在归档时一致且可解读”，不是“一定能重建出一模一样的数据库”。列覆盖测试是其中最容易被忽视、也最关键的一层。
- **主密钥是单点。** 归档加密密钥和签名密钥都由它派生，主密钥丢失意味着加密的归档包全部无法打开。部署说明要把主密钥备份和归档盘分开存放写成硬性要求。
- **密钥文件丢失的既有隐患。** 启动时只在 `audit_records` 为空时允许新建密钥，而完整性事件此时可能还在。归档把热库清空的情况会变多，密钥文件一旦同时丢失，新密钥会让链校验失败。已定随 P3、P4 修复：`HasAudits` 同时检查 `audit_records`、`integrity_events` 和归档目录表（5.7）。
- **明文会经过读取工具流出。** `cat` 和 `export` 的输出是明文，其中没有凭据值，但对话内容不遮蔽。使用者要对输出去向负责；帮助文本和部署说明里写明。
- **加密格式是新增的密码学代码。** 无论用库还是自己实现，都要有固定测试向量和篡改测试，评审时单独看。
- **内存预算是新的失效方式。** 现在的上限是隐式的（队列容量），改造后是显式的，而且内存里放的是明文。预算设小了会让大请求频繁走暂存，设大了有内存风险。默认值由 P0 的压测给出。
- **终结器单线程可能成为瓶颈。** 现在的解析 worker 也是单线程，所以不会比现在差，但“结束到可查询延迟”在高并发下可能不如预期。
- **完整性链持续增长。** 事件从不删除，启动校验把全部事件读进内存。归档让长期运行的库更常见，这个既有问题会更早显现。不在本 issue 范围内，建议另开 issue。
- **新的迁移版本不可被旧版本读取。** 本方案新增的每个迁移版本（第 6 节）都会让旧版本打不开审计存储，从 P0b 删索引的迁移 005 开始就是如此。回滚到旧版本前要从新到旧撤销对应的库表改动并删掉迁移记录，005 到 008 的步骤见 `doc/deployment/postgresql-migration.md`。
- **压缩后的解析结果旧版本读不了。** P0b 之后新写入的 `parsed_json_enc` 在达到 4 KiB 且压缩有收益时，密文里是 gzip 流。更早的版本不认识它，读这些行的详情和会话会报完整性错误，而且这不能用 SQL 撤销：行被完整性事件按密文签名，不能原地改写回去。回滚到 P0b 之前的版本意味着这段时间里解析不完整的记录在旧版本里看不了兜底会话；它们的 raw 仍然保留。P2 之后写入的行使用单一 Header 块和 `capture_version` 2，旧版本读不了，回滚前要先确认这段数据的去留。归档目录本身不受回滚影响。
- **归档里没有凭据原值。** 归档并移除之后，`Authorization`、`x-api-key` 这类值只剩名称、长度和 keyed 指纹，原值无法找回（5.5）。指纹只能用来核对一个已知的 Key，不能反推。
- **回滚手段。** P1 靠 parser 版本共存；P2 靠 `audit.write_path` 切回 `legacy`；P3、P4 靠 `archive.mode` 切回 `off`。注意从 `archive_then_delete` 切回 `off` 而 `retention_days > 0` 时，会立刻恢复没有归档的直接删除；只想暂停归档应当把 `retention_days` 设为 0（5.7）。已经发布的归档包始终保留，默认不自动销毁。已经从热库移除的数据不会因为回滚而回来。
  （2026-11-28 补记：第 3 阶段 A/B 之后维护者决定只保留 unified，legacy 写入路径已删去，P2 不再有切回的开关。`audit.write_path` 只接受省略或 `unified`；回滚 P2 只能换回上一个版本的二进制，不含迁移 007 的版本读不了采集版本 2 的行。见第 3 阶段设计实施记录 R.8 与部署说明 3.3。）

## 9. 不在范围内

## 附录 A：存储与 IO 实测

### A.1 口径

- 数据来自一个真实部署：版本 0.8.0，连续运行约 39 天，约 31.7 万条请求，没有开启 retention。流量几乎全部是 OpenAI Responses 的流式请求，平均每个请求体约 1.1 MB，平均每轮上下文约 220 个 item。
- 只读取了 PostgreSQL 的统计视图和聚合计数，没有读取任何内容。
- 大小按 10^9 字节计。库总大小约 74 GB。
- 该库的累计计数里包含一次 SQLite 导入，所以稳态 IO 取的是一个 5 分钟窗口内两次快照的差值。窗口里只有 33 条请求，只能看量级。
- 代码引用对应基线提交。别的部署比例会不同，尤其是协议构成不同或开启了 retention 的。

### A.2 空间构成

| 表 | 大小 | 占比 | 主要内容 |
| --- | --- | --- | --- |
| `body_chunks` | 31.0 GB | 42% | 异常请求保留的 raw，其中请求体 28.4 GB |
| `content_objects` | 10.0 GB | 13% | 内容对象；其中流式响应 envelope 4.3 GB |
| `parsed_results` | 8.2 GB | 11% | 几乎全是解析不完整时的兜底会话 JSON |
| `http_headers` | 7.5 GB | 10% | 堆 4.5 GB，主键索引 3.0 GB |
| `audit_analysis` | 6.6 GB | 9% | 其中 6.0 GB 是 TOAST 里的空洞 |
| `binary_objects` | 6.0 GB | 8% | 图片等二进制，按解码字节去重 |
| `analysis_detail_objects` | 1.4 GB | 2% | 洞察的派生明细 |
| 其余全部 | 3.6 GB | 5% | turn 图、时间线、阶段元数据、完整性事件等 |

真正的对话内容（去掉 envelope 的内容对象加图片）约 12 GB。其余 60 多 GB 是下面各项。

### A.3 空间节省点

| 序号 | 项目 | 占用 | 办法 | 现有数据能否回收 | 是否改摘要 |
| --- | --- | --- | --- | --- | --- |
| 1 | 异常请求保留的请求体 raw | 28.4 GB | 按侧决定保留（5.9） | 部分 | 否 |
| 2 | 解析不完整时的兜底会话 JSON | 7.8 GB | 压缩；raw 已保留时不存 | 部分，见下 | 否，但该列在摘要覆盖范围内，见下 |
| 3 | Header 逐值一行 | 7.5 GB | 每条 audit 一个压缩加密块（5.10） | 不能 | 是 |
| 4 | `audit_analysis` 的 TOAST 空洞 | 6.0 GB | 一次 `VACUUM FULL` | 能 | 否 |
| 5 | 流式响应的逐事件 SHA-256 | 4.3 GB | 紧凑描述加一个整体哈希 | 不能 | 否，需新 layout 版本 |

**第 1 项的构成。** 保留 raw 的 20,297 条请求里，20,289 条的请求体是完整的。

| 是否已有 turn | 情形 | 条数 | 请求体 raw |
| --- | --- | --- | --- |
| 有 | 上游返回 5xx，解析正常 | 11,389 | 9.2 GB |
| 有 | 客户端在响应前取消，或上游返回 4xx | 约 1,600 | 2.8 GB |
| 无 | 客户端在流中途取消 | 5,286 | 6.7 GB |
| 无 | 请求超过解析器的解码上限 | 79 | 6.3 GB |
| 无 | 响应事件异常或缺终止事件 | 1,788 | 3.3 GB |

- 有 turn 的 12.0 GB：对新数据只需改保留决定。现有数据改不了，语义摘要覆盖了每个阶段的保留状态（`integrity.go:697-733`）。
- 无 turn 的 16.4 GB：需要“只有请求的轮次”。超过解码上限的那 79 条在现有上限下省不掉。现有数据只有一部分可以原地处理：采集摘要不覆盖保留状态，也不覆盖解析结果，但 `reconstruction_failed` 事件的摘要覆盖这两者（见下面的更正）。所以只能原地处理只有 `capture_finalized` 事件的记录。

**第 2 项。** 7,188 条解析不完整的请求各存了一份未压缩的完整会话（`parser/worker.go:526-549`），平均 1.2 MB，最大 50 MB。同一条请求的 raw 也保留着，所以是存了两遍。P0b 对新写入的行先压缩再加密，旧行原样可读。5.9 的第二步做完后新数据不再产生这一项。

**对第 1、2 项的更正（第五版）。** 草案第四版写“这一列不在任何摘要里，可以原地重写”，这是错的。`parsed_results.parsed_json_enc` 的密文 SHA-256 通过 `appendParsedResultDigest` 同时进入 `semantic_compacted` 和 `reconstruction_failed` 两个事件的摘要；`reconstructionFailurePayloadDigest` 还覆盖 `body_streams.retention_state`（`postgres/integrity.go` 的 `semanticPayloadDigest`、`reconstructionFailurePayloadDigest`、`appendParsedResultDigest`，已对照基线代码复核）。由此：

- 对现有数据做任何原地回收，包括重写 `parsed_json_enc` 和改 `retention_state`，都必须跳过存在 `semantic_compacted` 或 `reconstruction_failed` 事件的记录，只处理只有 `capture_finalized` 的记录（5.9 第 4 点）。
- P0b 的兜底会话压缩只作用于新写入的行。摘要取的是落库密文的 SHA-256，新行按压缩后的密文签名，摘要格式不变；不回头重写旧行。

**第 3 项。** 每条请求 52 行，每行连同索引约 450 字节，而值平均只有 100 字节。两个阶段对之间逐条重复。少数几个很长的客户端自定义头占了值字节的大半。

**第 4 项。** 活数据最多 135 MB。空洞来自早期分析版本的大明细被重算替换。普通 `VACUUM` 只归还尾部的空页，需要 `VACUUM FULL`。这是一次性的运维操作，不涉及代码。

**第 5 项。** 流式响应的 envelope 为每个 SSE 事件存事件名、长度和十六进制 SHA-256（`parser/openai/auditmodel.go:240-248`）。实测 1.2 亿个事件，压缩后每个仍约 36 字节，比聚合出来的正文还大。整条流另有 `body_streams.sha256`。改成“事件名的游程编码、长度序列、一个覆盖全部事件的哈希”可以省掉其中绝大部分。它与 4.1 第 4 条要定义的未消费事件规则是同一处改动，应当一起设计。

小项：

- `content_objects_semantic_idx`（173 MB）在仓库里没有任何查询使用，可以删。它的键是随机哈希，每次插入对象都要弄脏一个随机页。
- 请求 envelope 共 0.5 GB：3.5 万个不同版本，平均 41 KB。很可能是工具定义留在 envelope 里没有拆成单独的对象，这一点没有看内容，需要确认。
- 另有几个索引的扫描次数是零，但它们是给 retention 的对象 GC 和外键检查用的，该部署没开 retention 才显示为零，不能据此删除。

### A.4 IO

**写。** 窗口内每条请求约 2.5 MB WAL。四个阶段各写一份压缩加密后的 Body，结束时删掉重复的两份，解析通过后再删剩下的两份，WAL 的大部分是这些 Body。4.2 第一步减半，第三步基本消除。窗口内整页镜像最多占 WAL 的四分之一。

**读。** 窗口内读了约 3.75 GB。

- 全部块访问的 82% 落在 `audit_records`、`audit_analysis`、`audit_project_identity` 三张表上，5 分钟里各被整表扫了数遍。对应的是两个回填的候选查询（`postgres/analysis_backfill_reader.go:36-51`，`postgres/org_writes.go:121-135`）：反连接、没有水位。全部记录都处理完以后，每一轮仍然要扫完整张表才能确认没有候选，开销随表线性增长。
- `body_chunks` 的 TOAST 读了 1.27 GB，而窗口内 33 条请求的 Body 合计只有约 45 MB。解析器读回解释不了这个量。

**writer 占用。** 每一轮里，`insertContentObjects` 对该轮引用的每一个对象都执行一次带完整密文的 `INSERT … ON CONFLICT DO NOTHING` 和一次核对用的 `SELECT`，已经存在的对象也不例外（`graph_writer.go:271-297`）。之前的查重已经把这些对象的密文读出、解密并逐字节比对过一遍（`auditmodel/prepare.go:255-277`），之后算语义摘要时又把全部密文读回来做哈希（`integrity.go:339-399`）。也就是说，每一轮都把整段上下文的密文在数据库和进程之间搬三趟。实测这些读大多命中缓存，耗的是唯一 writer 的时间和 CPU，而不是磁盘。

**行更新。** 按累计计数，`audit_records` 平均每行被更新 2.7 次，没有一次是 HOT 更新，因为被更新的状态列都在索引里；这张表的索引是堆的两倍多。4.2 第三步把终态、解析状态合进一次提交后，更新次数会降下来。

**数据库参数。** `compose.yaml` 没有给 PostgreSQL 传任何参数，全部是默认值：`shared_buffers` 128 MB，检查点间隔 5 分钟，`max_wal_size` 1 GB。对几十 GB 的库和按窗口推算每天约 20 GB 的 WAL 来说偏小。

### A.5 与各阶段的关系

已经被本方案覆盖的：

- raw 先写后删产生的 WAL：4.2。
- Header 和块逐行插入、每个操作一个 savepoint：4.2 第一步。
- 解析时从库里读回 raw：4.2 第二步。

本方案原先没有覆盖、现在补进来的：

| 项目 | 去向 |
| --- | --- |
| 异常请求只留响应侧 raw | 5.9 已定，随 P1 落地 |
| Header 存储形式 | 5.10 已定，随 P2 第一步落地 |
| 逐事件哈希改紧凑描述 | P1，与未消费事件规则一起 |
| 回填候选查询加水位 | P0b |
| 回填对必然失败的记录不反复重读 raw | P0b，先证实 A.6 的推断 |
| 对象写入只发送查重未命中的对象，已存在的用一次批量查询核对 | P0b |
| 算摘要时在数据库里求密文哈希，不把密文取回进程 | P0b |
| 兜底会话压缩后再加密 | P0b |
| 删除 `content_objects_semantic_idx` | P0b |
| `compose.yaml` 与部署说明里给出 PostgreSQL 参数建议 | P0b |
| `audit_analysis` 的一次性 `VACUUM FULL` | 写进部署说明，由运维执行 |

### A.6 没有证实的推断

### B.4 对附录 A.6 第一条推断的验证

A.6 的推断是：回填每一轮都在重试必然失败的记录，并重读它们保留的 raw。用真实的 parser 和分析器逐类测过（`internal/parser/backfill_cost_test.go` 等），结论是**对一部分记录成立，对另一部分不成立**：

| 记录类型 | 改动前每轮读取 Body 的次数 | 改动后 |
| --- | --- | --- |
| 请求超过解码上限（存为 `partial`、raw 保留，截断的请求不是合法 JSON，分析每次都失败） | 2（请求加响应），每轮 | 2 次，仅一次 |
| 分析每次都以等待也消除不了的错误失败 | 2，每轮 | 2 次，仅一次 |
| 项目标识保存一直失败（原来没有任何跳过记忆） | 1，每轮 | 1 次，仅一次 |
| 永久跳过的记录超过 4,096 条时（原跳过集合满了就整个丢弃） | 5,000 条里 5,000 条，每轮 | 5,000 次，仅一次 |
| 保存时存储故障 | 2，每轮 | 2 次，分别在 0、10、30、70 分钟，之后每 80 分钟，一直重试到故障结束 |

不成立的部分：每种 `backfillSkip*` 原因在跳过集合还记得它的时候，每个进程最多读一次；分析能成功的 `partial` 记录只读一次；没有请求体、raw 已释放、没有对应 parser、没有 turn 图或已被删除的记录，跳过时根本不读 Body。

所以附录 A.4 里那 1.27 GB 的 `body_chunks` 读取，最可能的来源是前四行。这仍然是推断：那个部署上没有逐条语句的统计，本轮也没有连接它。

顺带修掉的一个旧问题：存储在读 Body 的中途出错时，原来会把读到一半的内容当作证据去解析，这条记录随后被当作“没有请求体”永久跳过。现在这种情况按可重试处理。

### C.2 流式响应的存储形态

- **折叠。** 每条流折叠成该端点的非流式 body，parser 自己的会话也从这个折叠体读出。所以从 raw 解析和从图重建得到同一个会话，同一个回答流式与非流式也得到同一个会话。
- **拆分。** 折叠体走该协议非流式响应的同一段拆分代码，流式与非流式存出相同的 response item 对象；全量重发历史时，下一轮请求复用上一轮响应对象的情形与非流式相同。Responses 流另外把终态响应里回显的 `instructions` 和 `tools` 各存成一个对象，同一会话的各轮只存一次。
- **紧凑描述。** 事件名的游程编码、数据长度序列，加一个流哈希：`SHA-256("llmapi-logger/sse-events/v1" || 0x00 || 逐事件 uint64be(len(name)) || name || uint64be(len(data)) || data)`。解码规则写在模块 05 §2.3，不读代码也能实现，测试里钉了一个向量。505 个事件的描述是 288 字节，之前约 18 KB。
- **残余。** 清单外的事件整条保留；已消费事件里不读的字段按原嵌套位置保留；被后一个事件覆盖的旧值留在发出它的事件下。各协议消费哪些事件和字段，见模块 06、07、08 的 §5.1。测试给每种已消费事件类型及其嵌套对象注入未知字段，再加未知事件类型，要求全部能在不读 raw 的情况下从重建结果里找回。
- **上限。** 残余超过 1 MiB 时响应不规范化：记录得到只有请求的轮次，解析保持 `ok`、错误码 `response_not_normalized`，响应 raw 保留。
- **保真门槛。** `internal/parser/builtin/fidelity_test.go` 遍历注册表：每个有 normalizer 的 parser，夹具目录里交给它的每条流都要在两条路径上得到相同的会话、用量、工具调用数和停止原因。新协议注册 normalizer 后自动纳入，不通过就注册不上。

### C.3 按侧保留的规则（实现结果）

没有 verified turn 时什么都不释放。有 turn 时：

| 结果 | 请求侧 raw | 响应侧 raw |
| --- | --- | --- |
| 正常（转发完成、采集完整、2xx/3xx），轮次带响应 | 释放 | 释放 |
| 正常，但轮次不带响应（响应解析不完整，或残余超限） | 释放 | 保留 |
| `5xx`、`429`、`401`、`403`、`408`、`409`、`499`，或客户端取消 | 释放 | 保留 |
| `400`、`422` 且 `upstream_error_class` 非空 | 释放 | 保留 |
| `400`、`422` 且 `upstream_error_class` 为空 | 保留 | 保留 |
| 其他没有列出的非 2xx/3xx 状态码（维护者已确认） | 保留 | 保留 |
| 2xx/3xx 但转发或采集异常且不是客户端取消；没有状态码且不是客户端取消（待确认，现按保留） | 保留 | 保留 |

释放请求侧还要求：请求规范化并通过重建校验；两个请求阶段已合并（`request_sent.source_stage == request_received`），都完整，没有 `body_stage_mismatch`。保留优先于取消。

什么时候准备只有请求的轮次：解析是 `ok` 或 `partial`；采到了响应 Body；响应不完整、解析因响应而 `partial`，或 normalizer 以残余超限拒绝了响应；请求完整、没有错误码，单独解析请求得到 `ok`；去掉响应后规范化得到非 `none` 的请求 layout，并通过重建校验。任何一条不满足就不准备轮次，记录与改动前完全一样。这段逻辑在 worker 里，不需要各协议自己实现。

半截的回答：有 turn 的记录不再往 `parsed_json_enc` 里存 `conversation`。只有请求的轮次把会话里响应一侧的消息单独存在 `partial_response_messages` 下，读取时由 `query.MergePartialResponse` 接在重建出的请求消息之后并重排 `Index`。详情、会话分析用的会话、重建导出都走这一个函数；P3 的归档读取也要用它。

在 PostgreSQL 上逐类验证过 17 种结果：哪些阶段是 `metadata`、哪些是 `full`，只有被释放一侧的块被删除，完整性链和每个事件的载荷摘要都通过。一条 1 MB 请求的流中途取消，存储从 542,496 字节（请求 raw 270,965、响应 raw 488、兜底会话 271,043）降到 271,947 字节（响应 raw 488、解析结果 303、内容对象 271,156，后者与后续轮次共享）。

### C.4 Gemini

- 请求按 `contents[]` 逐条成对象，`systemInstruction` 比照 Anthropic 的 `system`。模型的回答与下一轮请求重发的历史是同一个对象：两轮测试里第二轮引用 4 个请求对象，只新插入 3 个。
- 流完整性：每个出现过的 candidate 都报告了 `finishReason`（`FINISH_REASON_UNSPECIFIED` 不算），或者提示被拦截。否则解析为 `partial`（`missing_finish_reason`），不验证响应，得到只有请求的轮次，响应 raw 保留。
- 没有可用的会话 key，按内容推断父子关系：带系统指令时从第三轮开始连上，不带时从第二轮。
- 不带 `alt=sse` 的 JSON 数组流整体当作 JSON body 存，没有事件描述和残余。

### C.6 图查询在规模上的表现，以及现有删除路径

压测里的表只有几千行，规划器在小表上选顺序扫描是对的，看不出查询在大表上会怎样。所以另外造了一个有规模的图（700 个会话、20,580 个轮次、70,420 条上下文操作、122,780 个内容对象，会话长度 1 到 200 轮），对保存一轮、重建一轮和算摘要时实际发出的每条语句取 `EXPLAIN (ANALYZE, BUFFERS)`，自定义计划和通用计划各看一遍（`internal/storage/postgres/graph_scale_plan_test.go`）。

- **所有语句都走索引**，读取量不超过一个会话的行数。子查询里的 `LIMIT` 和 `::text[]` 转换不妨碍主键索引。
- **没有会话 key 的轮次找父轮次候选，原来是例外，已经加索引。** `chooseTurnParent` 里按协议取最近 32 个轮次的查询（`c.protocol = $1 AND t.created_at_ns < $2 ORDER BY t.created_at_ns DESC, t.turn_id DESC LIMIT 32`），`turns` 上原来没有以 `created_at_ns` 开头的索引，于是顺序扫描全部轮次再排序。这条查询改动前就有，但第 2 阶段之后每个 Gemini 轮次、以及不带会话 key 的 Anthropic 和 OpenAI 轮次都走它，开销随 `turns` 表线性增长，而且发生在唯一 writer 的事务里。
  - 维护者批准后，迁移 006 加了索引 `turns_created_idx`（`turns (created_at_ns, turn_id)`），schema 版本升到 6（[模块 04](../features/04-sqlite-storage-and-migrations.md) §3.8，回滚见[部署文档](../deployment/postgresql-migration.md#回滚到-schema-版本-5)）。这条查询现在从最新的轮次沿索引往回走，找到第 32 个同协议轮次就停，自定义计划和强制通用计划都一样：

    | 20,580 个轮次的库 | 加索引前 | 加索引后 |
    | --- | --- | --- |
    | Gemini 候选：读轮次 / 会话 / 缓冲区 / 耗时 | 20,580 / 700 / 1,222 / 约 4.6 毫秒 | 218 / 80 / 431 / 约 0.3 毫秒 |
    | Anthropic 候选 | 20,580 / 700 / 1,222 / 约 5.3 毫秒 | 223 / 80 / 436 / 约 0.26 毫秒 |

    测试按种子算出“往回走到第 32 个同协议轮次”要读多少行，要求两种计划都恰好读这么多并且走这个索引。排序键 `(created_at_ns, turn_id)` 是全序（`turn_id` 是主键），`LIMIT` 在第 32 个匹配处停下，所以读取量只由数据决定；它约是全表的百分之一，而顺序扫描要读全表再排序，规划器不会在两次运行之间换计划。
  - **结果不变。** 排序里本来就有 `turn_id DESC` 作为并列时的次序，`turn_id` 的排序规则是 `"C"`，与索引相同。时间戳相同的轮次谁先谁后只由 `turn_id` 决定，与走不走索引无关。测试在九个轮次共用一个时间戳、跨会话跨协议的数据上，对每个协议和几个截止点（含恰好等于共用时间戳的）比较删掉索引时的参数形式（改动前的语句）与 writer 现在发的协议字面量语句（强制走索引、以及由规划器自选）的 32 行，逐行相同；“走不走索引结果都一样”靠的是这个测试和全序这一点。父轮次等价比对（`LLMAPI_TEST_PARENT_EQUIVALENCE=full`，2,500 个随机图）也在有索引的库上全量跑过，全部相同，但它两边发的是同一条候选查询、图又小，证明的是新旧两种走法在有索引时仍然一致，不是索引不改结果。协议写进语句之后又全量跑了一次：这时改动前的实现发参数形式、现在的实现发字面量形式，19,961 次保存的结果仍全部相同（115 次两边同样拒绝）。
  - **弱点：某个协议在更早的轮次里不足 32 个（协议是参数时，已补上，见下一条）。** 这时往回走找不够 32 个，要走完整个索引，每个轮次回表再关联一次会话。在 2 万个 OpenAI 轮次加 5 个 Gemini 轮次的库上测了 Gemini 查询（数字取 5 次热运行的中位数，本机）：

    | | 加索引前 | 加索引后，协议是参数 | 加索引后，协议写进语句 |
    | --- | --- | --- | --- |
    | 自定义计划 | 先按协议扫会话，再走 `turns_conversation_created_idx`：5 行，约 0.08 毫秒 | 相同 | 相同 |
    | 强制通用计划，5 个 Gemini 轮次 | 顺序扫描 20,005 行，919 缓冲区，约 3.6–5.6 毫秒 | 走完索引 20,005 行，约 4,014 缓冲区，约 6.0–6.6 毫秒 | 与自定义计划相同：5 行，约 0.13 毫秒 |
    | 强制通用计划，该协议还没有轮次 | 哈希关联的会话侧为空，几乎不读轮次，约 0.09 毫秒 | 走完索引 20,005 行，约 6.1 毫秒 | 0 行，约 0.09 毫秒 |

    自定义计划知道这个协议的会话很少，从会话那一侧查，索引不影响它（31.7 万个轮次时约 1.2 毫秒）。只有通用计划会走完整个索引，**这时比原来慢**：2 万个轮次时约慢一半、缓冲区约 4 倍，31.7 万个轮次时约 3.5 倍；该协议还没有任何轮次时，原来几乎不花时间，现在要走完整个索引。pgx 会缓存预编译语句，PostgreSQL 在五次执行之后可能改用通用计划。实测默认的 `plan_cache_mode = auto`：在这个偏斜的库上连续 15 次都留在自定义计划（只调 OpenAI、只调 Gemini、两者交替都是）；在 20,580 个轮次的混合库上另加 5 个轮次的冷门协议，按 Gemini 与 Anthropic 交替、只调 Gemini、三个协议轮流调 12 次，也都留在自定义计划，冷门协议和还没有轮次的协议各读 5 行和 0 行，约 0.1 毫秒。反过来，没有这个索引时，同一个混合库上 auto 在第 6 次起就换成通用计划（顺序扫描全部轮次）。所以走完整个索引是可能发生、但在两种库上都没有观察到的情形。把协议存到 `turns` 上能彻底解决，已决定现在不做。
  - **已经补上：协议写进语句。** 维护者选了不改库表的补救：协议只有 `openai`、`anthropic`、`gemini` 三个值（解析器名的前缀，来自路由配置），`graph_writer.go` 为每个值各备一条把协议写成字面量的语句，每个协议各是一条预编译语句，通用计划也按这个协议的统计来定。字面量是代码里的这三个常量，轮次的协议值只拿来和它们比较，不拼进语句；不在这三个里的值仍走参数形式，所以这里没有注入的路径。返回的行和顺序与参数形式相同。上表最后一列是改后的数字：冷门协议两种计划都从它的会话那一侧查，只读它自己的轮次，代价是顺序扫一遍会话表（31.7 万个轮次、3.2 万个会话时约 1 毫秒）。常见协议不变，两种计划仍沿索引走到第 32 个轮次：2 万个轮次和 31.7 万个轮次的库上都读 32 行（约 0.1 和 0.4–0.6 毫秒），20,580 个轮次的混合库上 Gemini 218 行、Anthropic 223 行、OpenAI 45 行，与改前相同。`TestKeylessCandidateSearchKnowsTheProtocolAtScale` 在 2 万和 31.7 万个轮次上钉住这些行数（冷门协议 5 行、没有轮次的协议 0 行、常见协议 32 行且走索引），两种计划都要满足；`-short` 时只跑 2 万。剩下的一点：如果统计过时，某个协议已经变常见而统计仍说它冷门，通用计划会从会话那一侧读这个协议的全部轮次，开销上限仍不超过原来的顺序扫描，下一次 `ANALYZE` 后计划随之更新。
  - 建索引的代价：31.7 万个轮次（堆 118 MB）本机约 0.11 秒，索引 12 MB。迁移在启动时的迁移事务里建索引，受 writer 连接的 30 秒 `statement_timeout` 约束；库大到可能超时，部署文档写了先并发手工建好的做法。
- **保存一轮时祖先链被重复走了 34 遍，已经改掉。** 选父轮次时 32 个候选各自从头走一遍祖先链，另有重建校验和写入时的摘要各走一遍。现在候选的链按从旧到新预先装进一个共享缓存，每条链只走一遍；重建校验只读新轮次自己的行，摘要直接用校验刚重建出的引用。评估顺序、比较规则和结果都没有动：把改动前的实现原样留在测试里，对 2,500 个随机图上的 19,961 次保存逐次比对（15,965 次按生产上限，3,996 次按调低的上限），父轮次、依据、置信度、上下文操作、完整性事件的摘要和 MAC 全部相同，其中 115 次在调低的上限下被两边同样拒绝。这组数字取自全量运行的日志；本附录早先写的“23,899 次、76 次被拒”是转述时算错的。完整比对约十分钟，默认只跑同一生成器的前一小段，设 `LLMAPI_TEST_PARENT_EQUIVALENCE=full` 跑全量。

| `previous_response_id` | 605 → 203 | 1,849 → 617 | 902 → 303 | 5,604 → 4,341 |
| 无 key 的 Gemini、Anthropic | 27,323 → 22,601 → 2,239 | 20,806 → 6,152 | 10,154 → 3,037 | 约 26,400 → 约 11,600 → 约 10,850 |

无 key 那一行的第二个数里有 20,580 个轮次是上面说的那次全表扫描，第三个数是加了迁移 006 的索引之后，候选查询只读约 220 个轮次。共享缓存只属于一次保存的事务，按每轮约 220 个上下文条目估算约 0.5 MB，引用总数超过 262,144 时退回原来的走法。

**现有的到期删除路径在新形态上没有问题。** `tests/integration/retention_shapes_test.go` 经真实的代理、解析 worker 和存储写入三种协议的会话，包含只有请求的轮次（被删的、留下的、父子都是的）、请求 raw 已释放而响应 raw 保留的记录、`429`、跨截止点共享的图片对象、Responses 回显的 `instructions` 和 `tools`、Gemini 被下一轮重发的回答，然后让每个会话的前一段到期，按每批 200 条和每批 1 条各跑一遍：

- 留下的轮次重建出的请求和响应引用与删除前相同，被删轮次的子轮次成为带检查点的根；
- 仍被引用的对象保留，只被已删轮次引用的对象被回收；
- 被删的 audit 在各表里不留行；
- 完整性链和载荷校验在删除后通过；
- 留下的记录经管理 API 读出的详情、重建导出和 raw 响应与删除前逐字节相同。

顺带确认的一点：Anthropic 的响应对象从不与下一轮请求共享。它的响应按 content block 存，而下一轮请求重发的是整条 message，两者不是同一个对象。带系统提示的 Anthropic 会话第二轮会另起一个根，这是 PR #54 带来的现状，已有测试固定。

### C.7 没有问维护者而做的取舍，以及待确认的问题

与方案正文不同或正文没有覆盖的地方，都按“不丢内容”的方向做了，列在这里等确认：

1. 5.9 没有点名的两种情形（状态码正常但转发或采集异常且不是客户端取消；没有状态码且不是客户端取消）保留请求 raw。保留优先于取消。
2. OpenAI Responses 流里每个 delta 默认带的 `obfuscation` 随机填充当作残余保留。它是单条流里残余的主要部分，约 2.3 万个 delta 的长流会因此超过残余上限。
3. Anthropic 流式工具参数解析成对象后按规范化 JSON 存，与非流式一致；流里那段文本原有的键顺序和空白不保留。
4. SSE 的注释行和 `id:`、`retry:` 字段一直被解码器丢弃，残余和流哈希都不覆盖。这是改动前就有的行为。
5. Gemini 的流完整性靠 `finishReason`。没有找到官方依据说明它只出现在最后一个 chunk；如果某个模型每个 chunk 都带 `STOP`，被干净截断的流会被标成完整。收到的内容不丢，丢的是“不完整”这个标记。
6. Gemini 每个 chunk 的 `usageMetadata` 快照都保留，约 1.3 万个 chunk 的流会超过残余上限。
7. 响应是不支持的编码或超过解码上限、而请求可用时，也得到只有请求的轮次。比 5.9 列出的情形宽，方向相同。
8. OpenAI 只有请求的轮次，洞察的会话归属现在取自轮次的会话，改动前没有轮次时取自会话 key 或推断。实时与回填一致，但与改动前的值不同。
9. 被取消和被截断的请求现在计入所在会话的轮次数。

需要维护者决定的四件事（第 1 件已决定）：

1. 是否为无 key 轮次的父轮次候选查询加索引 `turns (created_at_ns, turn_id)`（C.6）。**已批准并加上**：迁移 006，schema 版本 6。剩下一个待定的小问题：通用计划下协议轮次不足 32 个时的开销，见 C.6。
2. 是否提 `AnalysisVersion`。流式会话改由折叠体读出后，有两种证据的分析结果变了，方向都是流式与非流式变得一致：Anthropic 流里的 `server_tool_use`（如 web search）原来被算成一次工具调用，现在不算；Gemini 流在后续 chunk 重复发出相同的 `functionCall` 时原来去重，现在逐个计数。按模块 20 的规则这需要提版本，代价是回填重算全部历史。夹具目录全部交换的分析结果已固定成 golden 文件（`internal/parser/testdata/analysis_catalog.golden`），以后改流式读取会在那里显形。
3. 已发布的非流式 Responses layout 是否也把回显的 `instructions`、`tools` 拆出来去重（C.2）。
4. Skill 包的版本。参考文档里流式重建导出的描述改了，包的 `VERSION` 没动，同名包的内容和哈希会不同。客户端不解析导出内容，兼容性不受影响。
